# api-tests — инварианты

Отдельный npm-проект: контрактные тесты backend по HTTP, чёрный ящик. Запуск — `make test-api`.

## Главное правило
**Не импортировать ничего из `backend/src` и `frontend/src`.** Свой `package.json`, свой tsconfig, ноль зависимостей от исходников приложения. Тестируется реально запущенный сервис ровно так, как его увидит фронтенд.

Если тест «знает» про внутренние классы Nest — он проверяет не то, что задеплоено. Это отдельный пункт code-review и чек-листа приёмки.

## Как обращаться к сервису
- `request(process.env.API_URL ?? 'http://localhost:8080')` — supertest по базовому URL, **не** по инстансу Nest-приложения.
- Перед сьютом дождаться `GET /api/health` (хелпер `support/wait-for-health.ts`).
- В контейнере адрес — `http://backend:8080`, локально — `http://localhost:8080`. Только из env, не хардкодить.

## Данные
- База — `linkboard_test`, отдельная от dev-базы `linkboard`. Никогда не подключаться к `linkboard`.
- Изоляция — TRUNCATE между тестами через `support/db.ts`. Межтестовых зависимостей быть не должно: каждый тест сам готовит своё состояние.
- База общая на весь прогон, поэтому **один воркер** (`singleFork` / `workers: 1`), параллелить нельзя.
- Клики с историческими датами сидируются **прямым INSERT** — через API нельзя задать `occurred_at`. Ссылки — можно и через API.

## Что проверять
- Кейсы: `docs/testing/coverage-matrix.md`, префикс `API-`. Уровень выбора кейса — `docs/testing/strategy.md`.
- В каждом кейсе — инвариант конверта: ровно одно из `data` / `error` не `null`.
- Коды ошибок и HTTP-статусы сверять с `docs/api/error-codes.md`, а не с реализацией.

## Гонки
Клик по редиректу пишется **асинхронно после** ответа 302. Проверять счётчик poll-хелпером с таймаутом, а не `sleep` — иначе тест либо флакует, либо тормозит весь прогон.

## Запуск
`npm test` = `vitest run` (one-shot). Контейнер обязан завершаться сам, exit code пробрасывается в `make` — watch-режим ломает и то, и другое. Ретраи — 0: флак здесь означает реальный баг или гонку, а не повод перезапустить.
