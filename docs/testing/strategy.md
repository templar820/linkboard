# Тест-стратегия Linkboard

Статус: черновик к SYNC-1/SYNC-4. Дата: 2026-08-11.
Источники: `docs/plans/linkboard.md` (разделы 3, 5, 6), `sprints/11-08/sprint-plan.md` (T4, T9, T10, T14–T16, T20, T22–T24, SYNC-1..5).

Документ — исполнимая инструкция для агентов-автоматизаторов (`test-automator`, `backend-developer`, `frontend-developer`). Конкретные кейсы и их распределение по уровням — в `docs/testing/coverage-matrix.md`.

## 1. Пирамида тестирования проекта

| Уровень | Где живёт | Инструменты | Порядок величины кейсов | Что реально поднимается |
|---|---|---|---|---|
| Unit backend | `backend/src/**/*.spec.ts` | vitest, моки репозиториев | 27 | ничего |
| Unit frontend | `frontend/src/**/*.spec.tsx` | vitest + @testing-library/react + msw | 17 | ничего |
| **api-tests** | `api-tests/` (отдельный проект) | vitest + supertest | 55 | postgres + backend |
| **e2e-tests** | `e2e-tests/` (отдельный проект) | Playwright | 10 сценариев | postgres + backend + frontend |

Форма пирамиды намеренно классическая: много быстрых и дешёвых unit-тестов в основании, средний слой api-tests — единственное место, где перебираются граничные значения контракта против реальной БД, и узкая вершина из 10 e2e-сценариев, которые подтверждают, что собранный стек работает как единое целое. **api-tests, а не e2e, — основной инструмент перебора краевых случаев.** e2e не должен разрастаться пропорционально числу эндпоинтов — это прямой путь к медленному и флакующему прогону.

### 1.1. Что проверяется на каждом уровне

- **Unit backend** — чистая логика без внешних зависимостей на мокнутых репозиториях/часах: генерация и валидация кода, нормализация URL, поведение при ошибке записи клика, агрегатная арифметика StatsService (дозаполнение нулями, нормализация referer, группировка UA, UTC-граница суток), контракт `{ data, error }` на уровне интерцептора/фильтра.
- **Unit frontend** — чистые компоненты и hooks на моках HTTP (msw): рендер по данным, состояния loading/empty/error, вызовы API с правильным телом, клиентская логика (debounce, URL params, disabled-состояния).
- **api-tests** — HTTP-контракт реально запущенного backend: коды статусов, форма JSON, `error.code`, поведение с реальной БД (уникальные констрейнты, каскады, агрегаты по реальным данным, конкурентность записи клика). Это единственный уровень, который систематически перебирает граничные значения (пагинация, диапазоны дат, лимиты, 404/400/409/410).
- **e2e-tests** — то, что физически нельзя проверить без браузера: реальная навигация, clipboard, debounce как ощущается пользователем, состояние в адресной строке при перезагрузке, визуальная деградация UI, сквозная связка «клик по короткой ссылке → изменение в админке».

### 1.2. Что осознанно НЕ проверяется на каждом уровне (чтобы не дублировать между api-tests и e2e)

- **Unit backend** не поднимает БД/HTTP, не проверяет маршрутизацию и порядок регистрации модулей, не проверяет SQL-запросы и индексы — для этого нужна реальная БД, это зона api-tests.
- **Unit frontend** не делает реальных HTTP-запросов (только msw), не проверяет визуальный рендер в реальном браузере и не проверяет интеграцию с реальным backend.
- **api-tests** не рендерит и не импортирует ни строки React — ни одного `page.goto`. Любой кейс, для которого достаточно HTTP-запроса и ассерта над JSON/БД, проверяется здесь и **не переносится в e2e** только ради «более настоящей» проверки.
- **e2e-tests** не перебирает граничные значения API повторно (диапазоны дат, лимиты, коды ошибок по каждому эндпоинту) — это уже сделано в api-tests. На один сценарий — не больше одного-двух представительных случаев ошибки (например, 409 на alias, 500 через `page.route`), не полный реестр `error.code`.

## 2. Правило выбора уровня — алгоритм

Перед тем как писать новый тест-кейс, агент проходит по шагам последовательно и останавливается на первом подходящем:

1. **Кейс проверяет чистую бизнес-логику/алгоритм, которую можно изолировать моками (репозиторий, часы, конфиг)?** → Unit backend. Пример: генерация base62-кода, retry на 23505, дозаполнение нулями пропущенных дней.
2. **Кейс проверяет чистый UI-компонент/hook в изоляции с моком HTTP (msw)?** → Unit frontend. Пример: рендер таблицы по пропсам, disabled-состояние кнопки.
3. **Кейс проверяет HTTP-контракт эндпоинта (код статуса, форма JSON, `error.code`) и/или поведение с реальной БД (уникальность, каскад, агрегаты, конкурентная запись), но не требует браузера?** → api-tests.
4. **Кейс требует реального браузера и пользовательского взаимодействия (клики, формы, навигация между страницами, clipboard, несколько вкладок, URL адресной строки) и подтверждает, что весь стек работает вместе?** → e2e — но только если кейс укладывается в один из 10 сценариев раздела 5.4 архплана либо является его естественным расширением. **Не создавать новый e2e-сценарий ради одного edge-case, если его можно проверить в api-tests.**
5. Если кейс формально подходит и под п.3, и под п.4 (например, «выключенная ссылка отдаёт 410») — пишем на обоих уровнях **только если** он естественно возникает как часть уже описанного пользовательского пути. Не дублируем искусственно.

**Практическое правило при сомнении:** пиши в api-tests. Это дешевле, быстрее и стабильнее, чем e2e. В e2e поднимаемся только тогда, когда без браузера кейс не имеет смысла (визуальное состояние, clipboard, реальная навигация по короткой ссылке, debounce как UX, персистентность URL при перезагрузке).

## 3. Изоляция и управление данными

- Отдельная база `linkboard_test`, создаётся init-скриптом `docker/postgres/init.sql` (T7) в том же контейнере postgres. Dev-база `linkboard` тестами не используется никогда.
- Единый TRUNCATE-хелпер `support/db.ts` в `api-tests/` (T9) переиспользуется в `e2e-tests/` (T10) через `fixtures/db.ts` — не два разных механизма очистки, один источник правды.
- TRUNCATE выполняется явно по обеим таблицам с сохранением предсказуемых id между тестами:

  ```sql
  TRUNCATE TABLE click_events, links RESTART IDENTITY CASCADE;
  ```

- **Момент очистки — перед КАЖДЫМ тестом**, а не перед сьютом:
  - api-tests: `beforeEach` в каждом spec-файле (не `beforeAll`).
  - e2e-tests: `beforeEach` в `test.beforeEach` (глобальный `global-setup.ts` — только для первичной очистки и ожидания healthy стека перед всем прогоном).

  Причина: если очищать только перед сьютом, тесты внутри файла начинают неявно зависеть от порядка выполнения и друг от друга.

- **Запрет на межтестовые зависимости.** Каждый тест сам создаёт все данные, которые ему нужны, и не полагается на данные, оставленные другим тестом. Критерий: любой тест должен проходить будучи запущенным в одиночку (`--grep`/`-t` с одним test-кейсом) и в любом порядке.
- **Сидирование — два способа, и когда какой:**
  1. **Через публичное API** (`POST /api/links`, реальные переходы по `GET /:code`) — способ по умолчанию для api-tests (создание бизнес-объектов без искусственных дат) и **обязательный** способ для e2e согласно архплану 5.4: «подготовка данных — через API, а не кликами». В e2e реальная навигация по короткой ссылке допускается только тогда, когда сам сценарий это и проверяет (сценарий 4).
  2. **Прямой INSERT в `click_events`** через `support/seed.ts` — неизбежен для тестов агрегатов, которым нужны клики с конкретными историческими `occurred_at` (клики «7/30/90 дней назад», проверка границы UTC-суток для `clicksToday`, дозаполнение нулями). Через реальный HTTP-редирект нельзя проставить дату клика в прошлое — сервис всегда пишет `now()`. Правило: **если в кейсе важна ДАТА клика — прямой INSERT; если важен сам факт учёта клика при реальном переходе (302 → запись, 410 → клик НЕ пишется) — только реальный HTTP-запрос на `/:code`, в обход бизнес-логики не идём.**
- api-tests и e2e-tests используют одну и ту же `linkboard_test`, но запускаются **строго последовательно** (`make test` = unit → api → e2e), никогда параллельно друг другу — иначе конкурируют за TRUNCATE одной базы (риск R9 архплана).
- Внутри одного уровня тесты, обращающиеся к БД, тоже не должны выполняться в нескольких параллельных процессах против одной `linkboard_test`: `api-tests/vitest.config.ts` — `pool: 'forks'`, `poolOptions.forks.singleFork: true`; `e2e-tests/playwright.config.ts` — `workers: 1` для прогона против общей тестовой БД (на масштабе ~65 тестов итоговая длительность прогона это не проблема).

## 4. Особый риск: асинхронная запись клика после 302

`GET /:code` отвечает `302` немедленно, запись в `click_events` и инкремент `links.clicks_count` происходят **после** отправки ответа (fire-and-forget). Это классический источник гонок и флаков, если тестировать «в лоб». Правило по уровням:

- **Unit backend** (`RedirectService.spec.ts`): не тестируем реальное время — мокаем репозиторий и проверяем, что после формирования ответа вызывается метод записи клика; ошибка записи (мок бросает исключение) не пробрасывается наружу и только логируется (spy на logger). Таймингов здесь нет вообще.
- **api-tests**: после запроса `GET /:code` через supertest **нельзя** сразу проверять `clicksCount` — это гонка. Обязателен poll-хелпер с ограниченным таймаутом и интервалом (например, `waitFor(() => condition, { timeout: 2000, interval: 50 })` в `support/`), а не фиксированный `sleep`/`setTimeout`. Хелпер живёт в `api-tests/support/` и переиспользуется во всех спеках, где проверяется побочный эффект клика (`redirect.spec.ts`, `stats.spec.ts` при сидировании через реальные переходы).
- **e2e-tests**: только web-first assertions Playwright (`expect(locator).toHaveText(...)`, `toContainText`, `toBeVisible`) с их встроенным авто-ретраем в течение таймаута — они естественным образом дожидаются, пока UI (после `reload()`/повторного запроса react-query) отразит асинхронно записанный клик. Никакого `waitForTimeout`. Пример из сценария 4: переход в новой вкладке → возврат в админку → `reload()` → `expect(page.getByTestId('link-header-clicks-count')).toHaveText('1')` — таймаут assert'а (по умолчанию 5s, при необходимости увеличивается конфигом теста, а не sleep'ом) покрывает задержку записи.

## 5. Политика флаков

- **Единственный разрешённый способ ждать состояния в Playwright — web-first assertions.** `page.waitForTimeout()` запрещён во всех e2e-спеках без исключений; наличие — блокер на code-review (T27).
- **Ретраи:**
  - `api-tests`: `retries: 0` всегда. Это детерминированный чёрный ящик против реальной БД; ретраи маскируют настоящие гонки записи и делают отчёт бесполезным.
  - `e2e-tests`, обычный прогон разработки: `retries: 0` — флаки должны быть видны сразу, а не тонуть в автоматическом повторе.
  - `e2e-tests`, стабилизационный прогон (T25 и будущий CI): `retries: 1` максимум, с обязательным логированием, какой тест ушёл в ретрай — это не «тихо позеленело», а сигнал для расследования, попадающий в отчёт T25.
- `trace: 'on-first-retry'`, `video: 'retain-on-failure'` (уже заложены в `e2e-tests/playwright.config.ts`, T10) — при найденном флаке первым делом смотрим trace/video, не гадаем по логам.
- **Что делать с найденным флаком:**
  1. Завести запись с логом/trace/видео (issue или пункт в отчёте T25/T27).
  2. Если причина очевидна и чинится быстро (неверный селектор, отсутствие web-first assert, реальная гонка на бэкенде) — чинить сразу в этой же ветке, не откладывать.
  3. Если причина не ясна за разумное время — тест уходит в **карантин**: `test.fixme('...', { annotation: { type: 'issue', description: '<ссылка/номер>' } })`. `test.skip()` без привязанного тикета — запрещён, ловится на code-review (T27).
  4. Карантин не может пережить одну волну стабилизации T25 — к следующему прогону тест либо починен, либо сценарий переписан.
- **Критерий готовности (DoD-13 спринта):** `make test-e2e` зелёный **3 раза подряд** с `retries: 0`, на чистой БД перед каждым прогоном (`make db-reset`). Ответственный за фиксацию — T25.

## 6. Нефункциональные проверки в скоупе спринта

- **Health-check.** `GET /api/health` при поднятой БД → api-tests (`API-51`, обычный прогон). Юнит-тест здесь бессмыслен — контроллер тривиален, а полезная проверка требует реальной БД.
- **Поведение при упавшей БД (503 `DB_UNAVAILABLE`).** Требует останова контейнера postgres, что несовместимо с обычным прогоном `make test-api` (сломает соседние тесты и параллельные volumes). Решение: отдельный тегированный кейс `API-52` вне стандартного сьюта — отдельный npm-скрипт (например `test:health-degraded` в `api-tests/package.json`) или явный шаг в T25, который: поднимает стек → `docker compose stop postgres` → запрос `GET /api/health` ожидает 503 → `docker compose start postgres` → ждёт healthy. Не входит в `make test-api` по умолчанию, прогоняется вручную/в стабилизации и на architect-review (T28) как отдельный пункт чек-листа.
- **Деградация UI при 500.** Единственная нефункциональная проверка внутри стандартного e2e — сценарий 10 (`page.route` подменяет ответ на 500, приложение показывает `ErrorState` и не падает).

### Вне скоупа спринта

Нагрузочное тестирование, security-тестирование (кроме того, что уже покрыто функциональными кейсами `VALIDATION_ERROR` — это не отдельная security-практика, а часть контракта), тестирование производительности агрегатов на больших объёмах данных (зафиксировано как риск R10 архплана, проверяется на architect-review T28 через EXPLAIN, не тестами), rate limiting (сама фича вне скоупа v1), авторизация admin-panel (вне скоупа v1).

## 7. Definition of Done тестового трека

- Все кейсы из `docs/testing/coverage-matrix.md` реализованы (ни одного `TODO`).
- `make test-unit`, `make test-api`, `make test-e2e` зелёные по отдельности и через `make test` целиком, без ручных шагов между стадиями.
- Нет `.only`; нет `test.skip()`/`test.fixme()` без привязанного тикета.
- `api-tests/package.json` и `api-tests/tsconfig.json` не содержат зависимостей/путей на `backend/src` (проверяется грепом на code-review, T27, и в чек-листе приёмки спринта).
- Все селекторы в `e2e-tests/pages/*` — `data-testid`, ни одного CSS-класса или текстового селектора для действий (текст допустим только как объект ассерта).
- Три подряд зелёных прогона `make test-e2e` без ретраев перед сдачей на T25.
- Матрица покрытия закрыта к SYNC-4 (чек-лист — в `coverage-matrix.md`).

### Задел под CI

CI-пайплайн не реализуется в этом спринте (только заготовка `.github/`), но конфигурация тестового трека проектируется так, чтобы будущие workflow переиспользовали `make`-команды 1:1, без изменения тестового кода:

- `job unit` — `make test-unit`, триггер: каждый push, без внешней инфраструктуры.
- `job api` — `make test-api`, триггер: каждый push, поднимает postgres+backend через compose profile `test`.
- `job e2e` — `make test-e2e`, триггер: только PR (дороже и медленнее), поднимает полный стек через compose profile `e2e`, `retries: 1` (см. §5).
- Артефакты CI: HTML-отчёт Playwright (`e2e-tests/playwright-report/`) и trace/video упавших тестов — публикуются как build artifacts.

## 8. Соглашения об именовании и структуре

| Уровень | Файл | Структура | Пример |
|---|---|---|---|
| Unit backend | `x.service.spec.ts`, рядом с кодом | `describe(ClassName)` → `it('делает X, когда Y')` | `describe('CodeGeneratorService')` / `it('retries generation on unique violation (23505)')` |
| Unit frontend | `Component.spec.tsx`, рядом с компонентом (не в `__tests__/`) | `describe(ComponentName)` → `it(...)` | `describe('LinkForm')` / `it('shows CODE_TAKEN error under alias field')` |
| api-tests | один файл на ресурс: `links.spec.ts`, `redirect.spec.ts`, `stats.spec.ts`, `health.spec.ts`, `envelope.spec.ts` (сквозной) | `describe('POST /api/links')` → `it('returns 201 with 7-char code')` | см. `coverage-matrix.md`, префикс кейсов `API-xx` |
| e2e-tests | один файл на группу сценариев (`create-link.spec.ts`, `links-list.spec.ts`, `redirect-and-clicks.spec.ts`, `link-details.spec.ts`, `dashboard.spec.ts`) | `test.describe('Создание ссылки')` → `test('...', async ({ page }) => ...)` | префикс кейсов `E2E-01`..`E2E-10` |

- **Язык названий тестов** — английский (`it`/`test` описания), консистентно с экосистемой Jest/Vitest/Playwright; комментарии и данные в самих тестах могут быть на русском, если это упрощает читаемость доменных данных (например, `title: 'Августовская рассылка'`).
- **Селекторы — только `data-testid`.** Никогда CSS-класс, tag-селектор или текст элемента для взаимодействия (текст — только для ассертов через `toHaveText`/`toContainText`). Конвенция имени: `kebab-case`, `<сущность>-<роль>`, например: `link-form-submit`, `link-form-alias-error`, `links-table-row`, `links-table-empty-state`, `link-header-copy-button`, `link-header-clicks-count`, `link-header-active-toggle`, `dashboard-summary-clicks-today`, `links-toolbar-search`. Полный список обязательных `data-testid` по компонентам фиксируется на SYNC-1 вместе с фризом контракта API — ответственность фронтенд-задач (T6, T8, T17–T19) при ревью `qa-expert`.
- **Page Objects** (`e2e-tests/pages/*`): один класс на страницу (`LinksPage`, `LinkFormPage`, `LinkDetailsPage`, `DashboardPage`); методы — глаголы действия (`createLink()`, `toggleActive()`); геттеры локаторов — существительные (`get linksTableRows()`). Бизнес-ассерты — только в spec-файле, не внутри Page Object.
