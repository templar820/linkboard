## 2. T21 — что проверено

Отправная точка: в конце фазы 3 координатор вручную проверил `LinkDetailsPage` против реального dev-backend и увидел рабочие данные — это означало, что базовая интеграция, скорее всего, уже на месте, в отличие от того, что предполагал план. Агент подтвердил это систематически, а не поверил на слово:

- **msw не участвует в рантайме**: grep по `frontend/src/**` вне `test/` не находит импортов `msw` вне `.spec.tsx`; прод-бандл (`npm run build` → `grep msw dist/assets/*.js`) — пусто.
- **Создание ссылки**: успех → редирект + toast; дубликат `customCode` → 409 под полем; пустой `originalUrl` → 400 под полем.
- **Обработка ошибок в UI**: несуществующая ссылка (404), искусственный 500 (остановленный postgres) — везде `ErrorState` с «Повторить», без белого экрана.
- **Инвалидация кеша**: PATCH `isActive` мгновенно отражается в `LinksTable` и на дашборде без `F5`.
- **Пагинация/поиск/сортировка**: проверено на 25+ ссылках, засеянных через API; тестовые данные удалены после проверки.

**Побочная находка, не баг:** TanStack Query по умолчанию приостанавливает retry сетевых запросов, когда `document.visibilityState !== "visible"` — в фоновой вкладке браузерной песочницы это выглядело как вечный спиннер. Не воспроизводится в обычном сфокусированном окне. **Важно для T22–T24**: Playwright-тесты должны держать вкладку в фокусе, иначе получат тот же ложный эффект.

`make test-unit` после T21: 54 backend + 23 frontend, без изменений в тестах.

## 3. T10 — что создано

`e2e-tests/` с нуля: `package.json`/`tsconfig.json` (изолированный npm-проект, `@playwright/test@1.55.0` — версия синхронизирована с тегом образа в `Dockerfile`), `playwright.config.ts` (`chromium` + `webkit`, `trace: on-first-retry`, `video: retain-on-failure`, HTML-отчёт в примонтированную `playwright-report/`, один воркер — общая `linkboard_test`, как и в `api-tests`), `global-setup.ts` (тот же предохранитель на `linkboard_test`, что в `api-tests`), `fixtures/{api,db,pages,index}.ts` (сидирование через API, не клики по UI), `pages/{Links,LinkForm,LinkDetails,Dashboard}Page.ts` — локаторы строго по замороженному реестру `data-testid` (`docs/api/contract.md` §9).

**Проблема с адресами** (браузер Playwright внутри контейнера резолвит `localhost` как себя, не как `frontend`) решена по образцу `backend-test` из фазы 3: добавлен сервис `frontend-e2e` (profile `e2e`, порт не публикуется, `VITE_API_URL=http://backend-test:8080`), `e2e-tests` перенаправлен на `frontend-e2e`/`backend-test`. По ходу живой проверки агент нашёл и поправил ещё два места, без которых стек не поднимался:
- `backend-test.profiles` расширен до `["test", "e2e"]` — иначе Compose падает валидацией `depends_on` поперёк неактивного профиля.
- `backend-test.CORS_ORIGIN` захардкожен на `http://frontend-e2e:3000` — иначе браузер, обслуживаемый `frontend-e2e`, получал CORS-блок на каждый запрос к API.

Проверено живым прогоном (`docker compose --profile e2e build` + `make test-e2e` с одноразовым smoke-тестом, затем удалённым): `chromium` и `webkit` оба зелёные, HTML-отчёт корректно лёг в примонтированную директорию, exit code пробросился в `make`.

## 4. Что скорректировал координатор после отчёта агента

**Находка системы безопасности (не проигнорирована, проверена и исправлена).** Агент поставил `server.allowedHosts: true` в `frontend/vite.config.ts`, чтобы обойти защиту Vite от DNS rebinding (Host-заголовок `frontend-e2e:3000` иначе получает 403). Проблема: `vite.config.ts` — общий файл, использует его и обычный dev-сервис `frontend`, у которого порт **опубликован наружу** (`docker-compose.yml`, `"${FRONTEND_PORT:-3000}:3000"`). `allowedHosts: true` снимал защиту и с него, хотя обоснование агента в комментарии ошибочно ссылалось только на `frontend-e2e` (порт которого действительно не публикуется).

Исправлено на точечный список: `allowedHosts: ["frontend-e2e"]`. Проверено вживую (`docker compose exec backend-test node -e ...`): запрос с `Host: frontend-e2e:3000` → 200, запрос с произвольным `Host: evil.example:3000` → по-прежнему 403. Защита сохранена, разблокирован только нужный хост.

**Баг, найденный агентом для будущего трека, но не в его скоупе — исправлен сразу, раз нашли.** `frontend/src/components/links/LinksTable.tsx` не передавал `rowTestId`/`getRowDataId` в `Table` (в отличие от `TopLinksTable.tsx`/`ReferersTable.tsx`, где это сделано верно) — строки `links-table-row` и атрибут `data-id` не рендерились, хотя page object `LinksPage.row(linkId)` в `e2e-tests/` уже написан по замороженному контракту и ждёт именно их. Добавлены `rowTestId="links-table-row"` и `getRowDataId={(link) => link.id}` — по образцу, который уже был задокументирован прямо в JSDoc самого `Table`-компонента. Typecheck и `npm test` фронтенда (23/23) — без регрессий.
