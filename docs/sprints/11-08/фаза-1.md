## 3. Ключевые технические решения

### 3.1. Как `GET /:code` не перехватит `/api/*` (T5)

Вместо `setGlobalPrefix('api', { exclude: [...] })` выбраны **явные пути в контроллерах**: `@Controller('api/health')`, дальше `@Controller('api/links')`, `@Controller('api/stats')`, а редирект в T12 будет `@Controller()` + `@Get(':code')`.

Обоснование: `/api/*` — это всегда минимум два сегмента пути, `/:code` — ровно один, поэтому пересечение структурно невозможно **независимо от порядка регистрации модулей**. Вариант с `exclude` требовал бы ручного поддержания списка исключений при каждом новом модуле, и одна забытая строка воспроизводила бы риск R4 из плана спринта. Вырожденный случай `GET /api` без второго сегмента закрыт резерв-списком кодов (`api`, `health`) из контракта. Решение задокументировано в `backend/src/main.ts` — T12 достаточно добавить модуль, `main.ts` править не придётся.

### 3.2. BIGINT возвращается строкой (T7)

Драйвер `pg` отдаёт BIGINT как JS-строку, а контракт требует чисел (`"clicksCount": 1523`, не `"1523"`). На каждую BIGINT-колонку навешан `ValueTransformer`, приводящий значение к `number` при чтении. Для масштаба сервиса это безопасно — счётчики кликов и id далеки от `Number.MAX_SAFE_INTEGER`, а BIGINT в схеме оставлен как запас.

Побочный эффект: типы опций `@PrimaryGeneratedColumn` в TypeORM 0.3.31 не содержат поля `transformer`, поэтому первичные ключи объявлены через `@Column({ primary: true, generated: 'identity', generatedIdentity: 'ALWAYS', ... })`. В БД это даёт ровно `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` из DDL — отличается только способ объявления в коде.

Индекс `idx_links_created_at` требует `DESC`, чего декоратор `@Index` не умеет, — он добавлен в миграцию сырым SQL.

### 3.3. Версии зависимостей

- **TypeORM закреплён на `^0.3.31`**, хотя в реестре есть `1.1.0`. Вся архитектура задач T5–T7 (`DataSource`, `migrationsRun`, `autoLoadEntities`, `typeorm-ts-node-commonjs`) написана под API 0.3.x, и мажорный переход в начале спринта создал бы риск для T11–T13, которые будут писать репозитории по этому же API.
- **vitest поднят до `^3.2.7`** (планировался 2.x): с `vite@6` npm ставил вложенный `vite@5` внутрь `node_modules/vitest`, и конфликт типов двух версий Vite ломал `typecheck`.
- **TypeScript 5.7**, строгий режим включая `exactOptionalPropertyTypes` и `noUncheckedIndexedAccess` в обоих проектах.

### 3.4. Дизайн-система без новых зависимостей (T8)

Токены и компоненты сделаны на чистом CSS (переменные + CSS Modules) — без Tailwind, MUI и styled-components. Причина жёсткая: `package.json` и lock-файл были вне зоны ответственности T8, а сборка в Docker идёт через `npm ci`, поэтому расхождение lock-файла сломало бы образ. `git diff` по `package.json` и `package-lock.json` после T8 пуст.

Доступность заложена сразу: `ConfirmDialog` — полноценный модал с фокус-трапом, Escape и возвратом фокуса; `Toast` — корректный `aria-live`; глобальный `:focus-visible`; контраст по AA; для графика кликов различие не только цветом, но и `strokeDasharray`.

## 4. Найденный дефект — расхождение реализации с контрактом

**Что нашёл при интеграционной проверке:**

```
GET /api/nonexistent
→ HTTP 404
→ {"data":null,"error":{"code":"INTERNAL_ERROR","message":"Cannot GET /api/nonexistent"}}
```

`HttpExceptionFilter` оборачивает любой `HttpException`, брошенный не через `ApiException`, в код `INTERNAL_ERROR`, сохраняя исходный HTTP-статус. Поведение сознательное и задокументировано в коде фильтра, но **противоречит `docs/api/error-codes.md`**, где `INTERNAL_ERROR` объявлен исключительно как HTTP 500. Получается ответ, невозможный по контракту: код `INTERNAL_ERROR` со статусом 404.

**Почему это важно за пределами несуществующего маршрута.** Тот же путь сработает в T11–T13: если разработчик бросит штатный `new NotFoundException()` вместо `ApiException`, клиент получит `INTERNAL_ERROR` с 404 — контракт нарушен молча, без ошибки сборки и без падения теста, пока api-тест не проверит именно эту пару.

**Контракт заморожен на SYNC-1, поэтому чинить это самовольно я не стал.** Решение за координатором, вариантов два:

1. **Добавить в реестр код `NOT_FOUND`** (HTTP 404) для несуществующих маршрутов и вообще любых `NotFoundException` вне доменной логики. Правка контракта плюс правка фильтра.
2. **Оставить как есть**, но зафиксировать в `error-codes.md`, что `INTERNAL_ERROR` — это «непредвиденная ошибка с любым статусом», сняв привязку к 500. Правка только документации, но код становится менее информативным для фронтенда.

Рекомендую первый вариант: фронтенду важно отличать «маршрута нет» от «сервер сломался», а `ErrorState` для этих случаев должен показывать разный текст.

Побочно: сообщение `"Cannot GET /api/nonexistent"` — это сырой текст Nest. Утечки внутренностей тут нет, но по контракту сообщения должны быть нашими.
